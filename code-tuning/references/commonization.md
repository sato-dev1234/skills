# 共通化の観点

変更したコードが、既存の共通処理や補助関数で置き換えられる箇所を持たないかを見る。読み手は、共通の反復改善ルールを使う実行担当者と、この観点を担当する評価者。

## チェック項目

1. 既存ユーティリティ / 補助関数 / 共有モジュールで置き換えられる箇所がないか
2. 既存機能と重複する新規関数がないか
3. 手書きの文字列処理、手動のパス処理、独自の環境確認、場当たり的な型判定など、既存の共通処理を使える箇所がないか

## この観点だけの判定規則

重要度はコードチューニングの分類規則に従う。この観点では、置き換え先のヘルパーまたは共通処理を実コードベース内で確認できた場合だけ指摘を出す。

## この観点だけの指摘条件

この観点では指摘を出す条件を次で分ける:

- **置き換え先のヘルパー / 共通処理を実コードベース内で確認できた場合**: 指摘を出す。自動修正可能性はコードチューニングの判定規則に従う
- **置き換え先候補が推測でしか挙げられず、実コードで確認できなかった場合**: 指摘自体を出さない(推測修正は禁止 / 推測指摘も出力しない)。自動修正不能として残した件数には含めない

## この観点だけの自動修正可能性

置き換え先ヘルパー / 共通処理を実コードベース内で確認できたときだけ自動修正可能とする。確認できなければ指摘自体を出さない。

不具合検出の観点のセキュリティ的不具合(SQL / コマンド注入など)の修正で「パラメータ化問い合わせヘルパーの存在」が必要になる場合も、そのヘルパーを実コードベース内で確認できなければ修正案を提示するだけに留め自動修正不能とする(実コードで確認できれば自動修正可能)。

## 評価者へ渡す依頼

```
あなたはコード差分を共通化の観点で評価する読み取り専用の評価者です。修正はしません。

## 対象の差分
採用した差分全体を含める。

## この観点で見ること
1. 既存ユーティリティ / 補助関数 / 共有モジュールで置き換えられる箇所がないか
2. 既存機能と重複する新規関数がないか
3. 手書きの文字列処理、手動のパス処理、独自の環境確認、場当たり的な型判定など、既存の共通処理を使える箇所がないか

## 制約
- 置き換え先のヘルパー / 共通処理を実コードベース内で確認できた指摘だけを出す。推測でしか挙げられない置き換え先は指摘自体を出さない
- 読み取り専用。コードは修正しない

## 指摘の返し方
各指摘について次を添える:
- 対象ファイルと行
- 指摘の要約と内容
- 重要度 (critical / high / medium のいずれか。判断に迷えば書かなくてよい。最終判定は呼び出し側が決める)
- 修正可能性候補 (自動修正可能 / 自動修正不能。判断に迷えば書かなくてよい)
- 根拠 (行番号と該当コード片 1-3 行。行番号だけは不可)
- 修正案
```
