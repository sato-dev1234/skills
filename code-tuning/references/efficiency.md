# 効率の観点

変更したコードが、無駄な計算・取得・通知や、解放漏れを持たないかを見る。読み手は、共通の反復改善ルールを使う実行担当者と、この観点を担当する評価者。

## チェック項目

1. 重複計算、重複ファイル読み込み、重複 API 呼び出し、N+1。ループ内の追加クエリだけでなく、関数自身が単発でも、呼び出し側でループされる可能性が高い検索系 / 読み込み系の関数も含める。見分け方: 関数名が `find*` / `get*By*` / `load*` で始まり、外部公開されている(外部から呼び出される)もの
2. 並行でできる処理を順番に実行している
3. 起動時 / 要求ごと / レンダーごとのホットパスに不要な重い処理
4. ポーリング / インターバル / イベントハンドラの中で、変化がなくても毎回更新通知を出す無駄な更新。差分検出のガード不足。更新関数 / リデューサのコールバックを受けるラッパーが同一参照の返却を維持しない
5. 不要な事前存在確認 (TOCTOU アンチパターン)
6. 無制限に増えるデータ構造、後始末漏れ、イベントリスナーのリーク
7. 必要以上に広い範囲を読む処理 (ファイル全体を読んで一部しか使わない、全件取得して 1 件に絞る等)

## この観点だけの判定規則

この観点だけで重要度を上げる規則は無い。重要度はコードチューニングの分類規則に従う。

## この観点だけの自動修正可能性

この観点だけの例外は無い。コードチューニングの自動修正不能条件に従う。
