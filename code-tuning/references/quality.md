# 品質の観点

変更したコードが、保守性・理解容易性を損なう構造を持たないかを見る。読み手は、共通の反復改善ルールを使う実行担当者と、この観点を担当する評価者。

## チェック項目

1. 既存の状態と重複する状態、導出できるキャッシュ値、状態監視や副作用実行のためだけに分けられ、直接呼び出しで同じ結果を得られる処理
2. 既存構造を見直さずに引数だけ増やしている (引数の膨張)
3. 少しだけ違うコピーペースト
4. 抽象の境界を壊して内部詳細を漏らしている
5. 定数や列挙型 (文字列リテラルの直和型) で表せるところに生の文字列が散らばっている
6. レイアウト上の意味がない JSX 入れ子、既存コンポーネントのプロパティで表現できるラッパー
7. 3 段以上のネスト条件 (三項連鎖、入れ子 if/else、入れ子 switch)
8. helper、wrapper、worker などへ処理を分けた結果、呼び出し元から読める流れを追うコストが、境界としての価値や現在の配置価値を上回っている

## helper / wrapper / worker の評価手順

品質観点では、helper、wrapper、worker の問題を、評価者が気づいた候補の列挙に任せない。評価前に候補集合と境界索引を作り、評価者は境界索引に載った境界をすべて判定する。

境界とは、呼び出し元から分けられた名前付き処理単位である。関数、メソッド、関数式、コールバック、helper、wrapper、worker、local function は境界になりうる。

この手順で扱う記録は次のとおり。

| 記録 | 役割 |
|---|---|
| 候補集合 | 差分 hunk が入る名前付き処理と、その同じファイル内の呼び出し辺から、評価対象になりうる境界を列挙する |
| 境界索引 | 候補集合から品質観点で評価する境界を固定する |
| 境界判定 | 境界ごとに指摘、維持、評価不能を決める |
| 指摘一覧 | 指摘に分類した境界を通常の評価指摘として返す |

候補集合と境界索引は、品質観点の評価者に作らせない。境界判定の前に、実行担当者または補助評価者が、差分と同じファイル内の呼び出し関係から作る。

ここでいう補助評価者は、実行担当者の依頼を受け、候補集合と境界索引だけを読み取り専用で作る担当である。補助評価者は境界を指摘、維持、評価不能へ分類しない。

### 候補集合

候補集合は、helper / wrapper / worker かどうかを意味判断しない。差分と同じファイル内の名前付き処理と呼び出し辺だけで作る。

候補集合は次の手順で作る。

1. 差分 hunk が入る名前付き処理を列挙する。
2. その名前付き処理ごとに、同じファイル内の呼び出し元を列挙する。
3. その名前付き処理ごとに、同じファイル内の直接呼び出し先を列挙する。
4. 直接呼び出し先が同じファイル内の名前付き処理なら、その呼び出し先の直接呼び出し先も一段だけ列挙する。
5. ここまでで得た境界に安定 ID を付ける。

この手順では、entry wrapper、薄い wrapper、worker と呼べるかどうかを判断しない。探索範囲を読めない場合、または呼び出し関係の有無を根拠行付きで示せない場合は、候補集合を作れないため品質観点を評価不能にする。

候補集合の各行は次を持つ。

```text
- 候補 ID:
- 境界:
- 境界の根拠行:
- 差分 hunk との関係:
- 呼び出し元と根拠行:
- 呼び出し先と根拠行:
- 同じファイル内の呼び出し元数:
```

候補 ID は、同じ差分を再評価しても照合できる形にする。基本形は次とする。

```text
<file path>::<boundary name>::<boundary start line>
```

`file path` はリポジトリルートからの相対パスに正規化する。区切りは `/` にそろえ、大小文字を区別しないファイルシステムでは比較時に小文字化する。

匿名の関数式やコールバックは、親の境界名、呼び出し行、同じ行内の出現順を使う。

```text
<file path>::<parent boundary>::callback@<call line>#<ordinal>
```

呼び出し元または呼び出し先がない場合も、探索範囲と「該当なし」の根拠を記録する。空欄や未調査を該当なしとして扱わない。

### 境界索引

境界索引は候補集合から作る。候補集合にある境界を、品質観点の評価対象から外す場合は、外す理由と根拠行を記録する。

境界索引は次の規則で作る。

| 規則 | 扱い |
|---|---|
| 候補集合にある境界 | すべて境界索引へ入れる |
| 品質観点で判定しない理由がある境界 | 境界索引には残し、判定対象外の理由、探索範囲、根拠行を記録する |
| wrapper / worker か迷う境界 | 外さず、境界索引へ入れる |
| 呼び出し元数を示せない境界 | 評価不能として境界索引へ入れる |

境界索引には、各境界について次を必ず記録する。

```text
- 索引 ID:
- 候補 ID:
- 境界:
- 境界の根拠行:
- 呼び出し元と根拠行:
- 同じファイル内の呼び出し元数:
- 呼び出し先と根拠行:
- 索引に入れた理由:
- 判定対象外にする場合の理由:
- 判定対象外にする場合の探索範囲:
- 評価不能にする場合の理由:
- 評価不能にする場合の探索範囲:
```

判定対象外にする理由と評価不能にする理由は別の記録項目として扱う。品質観点で評価しない判断を記録する場合は判定対象外の項目を使い、呼び出し関係、根拠行、呼び出し元数、価値判定の不足を記録する場合は評価不能の項目を使う。

索引 ID は候補 ID から作る。

```text
index::<候補 ID>
```

境界索引を作る時点で、候補集合との差分を記録する。

```text
- 候補集合にあり境界索引にもある ID:
- 候補集合にあるが境界索引にない ID:
- 境界索引にあるが候補集合にない ID:
```

候補集合にある ID はすべて境界索引に残す。候補集合にあるが境界索引にない ID が残る場合、品質観点は評価不能にする。境界索引にあるが候補集合にない ID は、追加理由と根拠行を示す。

### 境界判定

境界判定では、境界索引に載った境界をすべて、指摘、維持、評価不能のどれかに分類する。

| 分類 | 条件 |
|---|---|
| 指摘 | 境界または配置が、読むための移動コストに見合わない |
| 維持 | 境界価値と配置価値を別々のコード事実で示せる |
| 評価不能 | 呼び出し関係、根拠行、呼び出し元数、価値判定のいずれかが足りない |

境界索引で判定対象外の理由を記録した境界も、境界判定には載せる。判定対象外の理由だけでは維持にせず、品質観点として評価できない境界として評価不能にする。

判定では、次を分ける。

| 判定 | 問うこと |
|---|---|
| 処理価値 | 境界内の処理自体に残す価値があるか |
| 境界価値 | 呼び出し元から離した名前付き単位にする価値があるか |
| 配置価値 | 現在の場所に置く価値があるか |

処理価値だけでは維持できない。境界価値があっても、対象ファイルのトップレベルに置く配置価値がなければ現在の配置は維持できない。対象ファイルのトップレベルに置く境界は、呼び出し元内に置く local function と区別する。

境界判定は次を持つ。

```text
- 判定 ID:
- 索引 ID:
- 候補 ID:
- 判定:
- 判定理由:
- 該当する指摘条件:
- 指摘条件を満たさない場合の理由:
```

判定 ID は索引 ID から作る。

```text
judgement::<索引 ID>
```

維持にする場合も、該当しそうな指摘条件を挙げ、その条件をなぜ満たさないかをコード事実で示す。

指摘にする場合、指摘 ID は判定 ID から作る。

```text
finding::<判定 ID>
```

境界判定で指摘にした境界は、一つの判定 ID につき一つの指摘 ID を持つ。複数の問題が同じ境界にある場合は、その指摘 ID の中に複数の理由として書く。別の指摘 ID へ分けない。

### 指摘にする境界

次の境界は、維持根拠が示されない限り指摘にする。

| 境界 | 判定条件 | 修正方針 |
|---|---|---|
| 単一呼び出しの条件正規化 helper | 同じファイル内の呼び出し元が 1 つで、境界内の主処理が条件の整形または既定値選択に留まり、呼び出し元で入力から判定までを直線的に読める | 呼び出し元へ inline、または呼び出し元へ統合する |
| 単一呼び出しの entry wrapper | 同じファイル内の呼び出し元が 1 つで、処理の大半を別の worker へ渡し、公開契約、再利用、安全性の閉じ込めを持たない | 呼び出し元へ統合する |
| worker として価値はあるが対象ファイルのトップレベルに置く根拠がない境界 | 再帰状態、累積状態、探索位置などを閉じているが、複数利用、公開契約、拡張軸との一致を示せない | local function 化する |
| 既存処理へ委譲しているだけの wrapper | 入力をほぼ変えずに既存処理へ渡し、wrapper 自体の契約や、危険操作または状態変更を安全に行う順序を作っていない | 委譲先を呼び出し元から直接使う |
| 前提確認だけを包む薄い wrapper | 前提確認はあるが、危険操作、例外処理、状態保護を同じ境界内で閉じていない | 実際の危険操作または呼び出し元の近くへ移す |

たとえば評価者が付けた「仕様境界」「入口」「worker」「安全境界」のような分類名だけでは維持できない。

### 維持できる境界

境界を維持できるのは、境界価値と配置価値をどちらも示せる場合だけである。

| 価値 | 根拠になるコード事実 |
|---|---|
| 公開契約 | 他ファイル、テスト、CLI、module export などが境界名を契約として使っている |
| 現在の再利用 | 複数の呼び出し元が同じ前提と戻り値契約で使っている |
| 安全性の閉じ込め | 危険操作または状態変更、例外処理、状態保護、これらと同じ境界から分離できない前提確認が閉じている |
| アルゴリズム境界 | 再帰状態、累積状態、探索位置などを独立した処理単位として閉じている |
| 拡張軸との一致 | provider、kind、登録表、分岐表など、既存の増減単位と一致している |

前提確認だけの wrapper は、安全性の閉じ込めではない。危険操作または状態変更と同じ境界から分離できる前提確認も、安全性の閉じ込めではない。

安全性の閉じ込めを維持理由にする場合は、次を別々に示す。

```text
- 危険操作または状態変更の実体行:
- 例外処理または状態保護の実体行:
- 前提確認の実体行:
- 前提確認を境界外へ分離できない理由:
```

これらを示せない場合、安全性の閉じ込めを維持理由にしない。

### 完了確認

品質観点の結果は、次をすべて満たす場合だけ採用する。

- 候補集合、境界索引、境界判定、指摘一覧が分かれている。
- 候補集合にある候補 ID が、境界索引にすべて含まれている。
- 境界索引が、品質観点の評価者とは別に作られている。
- 境界索引に載る各境界について、索引に入れた理由、判定対象外にする理由、評価不能にする理由に対応する探索範囲と根拠行が示されている。
- 境界索引に載った索引 ID が、すべて境界判定に載っている。
- 境界判定にある索引 ID が、すべて境界索引に存在している。
- 境界判定に、判定 ID、索引 ID、候補 ID がある。
- 指摘にした判定 ID が、すべて指摘一覧に載っている。
- 指摘一覧にある判定 ID が、すべて指摘に分類された境界判定に存在している。
- 指摘一覧には、指摘 ID、判定 ID、索引 ID、候補 ID がある。
- 指摘 ID が `finding::<判定 ID>` の形で作られている。
- 維持にした境界に、境界価値と配置価値の別々のコード事実がある。
- 単一呼び出し判定に使う呼び出し元数が、同じファイル内の実呼び出し数として示されている。
- 評価不能の境界が一つでも残る場合、品質観点全体を評価不能にする。

この条件を満たさない場合は評価不能にする。部分的に有用な指摘が含まれていても、品質観点全体としては未完了である。

## この観点だけの判定規則

helper / wrapper / worker の評価手順で指摘に分類した問題は、保守性と理解容易性への影響があるため medium 以上にする。重要度はコードチューニングの分類規則に従い、既存の high 条件に当たる場合は high にする。

## この観点だけの自動修正可能性

引数の膨張(既存構造を見直さずに引数だけ増やしている)は、本質的修正に責務分割が必要なため、常に自動修正不能(設計判断)とする。

helper / wrapper / worker の評価手順で出た指摘は、公開契約、安全性の閉じ込め、現在の再利用単位を変えず、対象ファイル内で完結する修正だけを自動修正可能にする。

それ以外のチェック項目は、コードチューニングの自動修正不能条件に従う。

## 評価者へ渡す依頼

実行担当者は、この観点の評価者へ依頼する前に、候補集合と境界索引を依頼に含める。候補集合と境界索引は、実行担当者または補助評価者が事前に作る。依頼には、採用した差分全体、対象ファイル、対象外ファイル、候補集合、境界索引、読み取り専用制約を含める。

```
あなたはコード差分を品質の観点で評価する読み取り専用の評価者です。修正はしません。

## 対象の差分
採用した差分全体を含める。

## 対象ファイル
評価対象ファイルの一覧を含める。

## 対象外ファイル
評価対象外にしたファイルの一覧を含める。

## 候補集合
実行担当者または補助評価者が事前に作った候補集合を含める。

## 境界索引
実行担当者または補助評価者が事前に作った境界索引を含める。

## この観点で見ること
1. 既存の状態と重複する状態、導出できるキャッシュ値、状態監視や副作用実行のためだけに分けられ、直接呼び出しで同じ結果を得られる処理
2. 既存構造を見直さずに引数だけ増やしている (引数の膨張)
3. 少しだけ違うコピーペースト
4. 抽象の境界を壊して内部詳細を漏らしている
5. 定数や列挙型 (文字列リテラルの直和型) で表せるところに生の文字列が散らばっている
6. レイアウト上の意味がない JSX 入れ子、既存コンポーネントのプロパティで表現できるラッパー
7. 3 段以上のネスト条件 (三項連鎖、入れ子 if/else、入れ子 switch)
8. helper、wrapper、worker などへ処理を分けた結果、呼び出し元から読める流れを追うコストが、境界としての価値や現在の配置価値を上回っている

## 制約
- 候補集合と境界索引は作り直さず、渡された ID を使う
- 境界索引にある境界はすべて境界判定へ載せる
- 境界判定で指摘にした境界はすべて指摘一覧へ載せる
- 維持にする場合も、該当しそうな指摘条件と、それを満たさない理由をコード事実で示す
- 引数の膨張の指摘は自動修正不能として返す(責務分割の設計判断が要るため)
- 読み取り専用。コードは修正しない

## 境界判定の返し方
境界ごとに次を返す:
- 判定 ID
- 索引 ID
- 候補 ID
- 判定 (指摘 / 維持 / 評価不能)
- 判定理由
- 該当する指摘条件
- 指摘条件を満たさない場合の理由

## 指摘の返し方
各指摘について次を添える:
- 指摘 ID
- 判定 ID
- 索引 ID
- 候補 ID
- 対象ファイルと行
- 指摘の要約と内容
- 重要度 (critical / high / medium のいずれか。判断に迷えば書かなくてよい。最終判定は呼び出し側が決める)
- 修正可能性候補 (自動修正可能 / 自動修正不能。判断に迷えば書かなくてよい)
- 根拠 (行番号と該当コード片 1-3 行。行番号だけは不可)
- 修正案
```
