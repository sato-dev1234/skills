# コードチューニングの対象と修正範囲

このファイルは、コードチューニングで扱う対象、評価、指摘の扱い、修正範囲を定める。評価者の起動、評価結果の整理、重複指摘の統合、修正、再評価、起動できない場合の扱いは共通の反復改善ルールに従う。判定項目の詳細は観点別の参照資料、停止判断と出力規則は完了判定の参照資料を正本にする。

## 対象

### 入力

確認対象の差分は次で決める。

| 条件 | 扱い |
|---|---|
| 依頼で差分取得コマンドが指定されている | 指定されたコマンドを採用する |
| 依頼で差分文字列、差分ファイル、対象ファイルが明示されている | 明示された入力を確認対象にする |
| 指定がない | 現在の作業ツリーと最後のコミットとの差分を見る |
| 未追跡ファイルがある | バージョン管理システムで確認し、新規追加ファイルとして内容を読む |
| バージョン管理システムが使えない、または確認対象が空である | 「確認対象が特定できない」と明示して対象外停止にする |

会話履歴、直前編集ファイル、更新時刻を根拠に確認対象を補わない。

### 対象判定

| 入力 | 対象判定 | 扱い |
|---|---|---|
| ソースコードの変更 (テスト、コメント以外) | 対象 | 対象ファイルだけを評価対象にする |
| テストファイル変更のみ | 対象外 | テスト品質を担当する skill を示す |
| ソースファイルだが差分の追加行と削除行がすべてコメント行 | 対象外 | コメントとテスト命名を担当する skill を示す |
| 設定、文書、画像、ロックファイル | 対象外 | 評価せず対象外として報告する |

テストファイルは、テスト専用ディレクトリ、テスト用途のファイル名、言語ごとの標準的なテスト用サフィックスで判定する。

### 対象範囲

確認対象ファイル内のうち、差分に現れた関数またはメソッド本体は、その関数全体を評価対象とする。差分外の関数、メソッド、他ファイルは評価対象にしない。読み取りは必要に応じて行ってよい。

品質観点で関数式、コールバック、local function などを境界として扱う場合は、その境界を含む関数またはメソッド本体を対象範囲にする。匿名コールバックのように名前だけで識別できない境界も、品質の参照資料で示す識別方法で扱う。境界そのものの判定に必要な呼び出し元、呼び出し先、呼び出し元数は、対象ファイル内に限って読む。

対象ファイルと対象外ファイルが混在する場合は、対象ファイルだけを評価対象にする。対象外ファイルは評価対象に含めず、担当スキルがある場合は出力で示す。

### 根拠の示し方

指摘の根拠となる行番号は変更後ファイルの行番号で記す。実ファイルを読めるなら実ファイルの行番号を正とする。読めない場合は差分ヘッダにある変更後側の開始行を起点に算出する。差分ヘッダの宣言行数と実際の行数が食い違う場合は、実際の行を数えた値を優先する。

実ファイルを読めず、差分ヘッダからも変更後ファイルの行番号を算出できない場合は、正確な行番号を作らない。提示差分内の変更後側相対位置と該当コード片で根拠を示し、正確な変更後ファイル行番号は不明として扱う。

### 対象外時の扱い

対象外として停止する場合は、停止理由、確認した入力、評価を実施していない事実を出力する。指摘、修正案、検証結果を混ぜない。

## 評価

### 評価観点

各観点のチェック項目、観点ごとの判定規則、評価者へ渡す依頼は参照資料に従う。

| 評価観点 | 参照資料の責務 | 読む資料 |
|---|---|---|
| 共通化 | 既存の共通処理や補助関数で置き換えられる箇所の評価 | 共通化の参照資料 |
| 品質 | 保守性と理解容易性を損なう構造の評価 | 品質の参照資料 |
| 効率 | 無駄な計算、取得、通知、解放漏れの評価 | 効率の参照資料 |
| 不具合検出 (セキュリティ的不具合を含む) | 実行時不具合とセキュリティ的不具合の評価 | 不具合検出の参照資料 |

この表にある各評価観点は、共通の反復改善ルールでいう評価の区切りとして扱う。観点ごとの評価者は対象を変更せず、修正、評価結果の統合、再評価、完了判定は共通の反復改善ルールと完了判定の参照資料に従う。

### 評価者へ渡す情報

各評価観点の依頼には、採用した差分全体、対象ファイル、対象外ファイルの一覧、読み取り専用制約を含める。観点別の参照資料が、候補集合、索引、照合表などの事前成果物を定める場合は、それらも依頼に含める。評価者はコードを修正しない。

### 責務外

コメント・テスト命名の整備、テスト品質、受入条件との整合は、それぞれを担当する skill の責務である。

## 指摘の扱い

### 評価結果の必須情報

評価者の返却は、共通の反復改善ルールの `指摘あり`、`指摘なし`、`評価不能` に整理する。コードチューニングでは次の情報を必須にする。

| 状態 | 必須情報 |
|---|---|
| 指摘あり | 評価観点、対象ファイルと行、指摘の要約と内容、重要度候補、修正可能性候補、根拠コード、修正案、評価者が迷った点 |
| 指摘なし | 評価観点、確認範囲、該当指摘なしの理由、評価者が迷った点 |
| 評価不能 | 評価観点、理由、不足入力、確認できた範囲、評価者が迷った点 |

観点別の参照資料が必須返却項目、事前成果物、照合条件、または評価不能条件を定める場合は、それらも必須情報に含める。必須返却項目が欠けている返却、または事前成果物と返却結果の照合条件を満たさない返却は、指摘なしではなく評価不能に整理する。

指摘の根拠は、行番号と該当コード片 1-3 行を最小要件とする。行番号のみは不可。

入力がファイル一覧、変更要約、またはコード片を含まない抜粋だけで、根拠コードの最小要件を満たせない場合は、対象判定と必要な評価観点の整理までに留める。観点別指摘は評価不能として扱い、根拠コードを推測して作らない。

### 重複指摘のまとめ方

評価観点、対象ファイル、問題箇所、落ちた判定項目、修正意図で同じ問題かを判定する。同じ箇所でも、観点ごとに独立した修正意図がある場合は別件にする。観点が違っても、同じ箇所への単一の置換で複数観点の指摘が同時に解消する場合は統合してよい。

### 分類

各指摘の重要度は、当てはまる最も重い段階を採る。観点ごとの重要度を上げる規則は参照資料に従う。

| 重要度 | 当てはまる状態 |
|---|---|
| critical | セキュリティ的不具合で実害が一意に判断できる。データ破壊、権限逸脱、主要機能を壊す可能性が高い |
| high | 一般的な入力経路の機能が止まる。引数の膨張、重複コピペ、抽象境界の漏れ、3 段以上のネスト条件、既存ユーティリティ未利用がある。N+1、広範囲取得、ホットパスへの重い処理、確認時点と使用時点のずれによる不具合 (TOCTOU)、メモリリークがある |
| medium | critical / high には当たらないが、保守性、理解容易性、性能への影響がある。loose equality、軽微な型不整合、生の文字列散在がある |

SQL / コマンド / コードを文字列連結やテンプレート展開で組み立て、リクエスト値、外部入力由来の値、または呼び出し元から未検証の値として渡ることを確認できる関数引数がそのまま実行内容へ混入する場合は critical とする。関数引数であることだけを外部入力由来の根拠にしない。値の由来が差分から確認できず、実行内容の改変可能性も実コードから判断できない場合は high 以下に留める。

これらより軽い問題は出力しない。本当に害があるなら medium 以上に格上げするか、判定を取り下げる。

### 自動修正可能性

次のいずれかに当たる指摘は自動修正不能とする。

- 確認対象が差分文字列だけ、会話上の抜粋だけ、または読み取り専用資料だけで、書き換え可能な実ファイルを特定できない。
- 修正案が依存するライブラリ、フレームワーク、外部サービスの API 仕様または既存の呼び出し形を、対象コード、依存関係、同一リポジトリ内の資料から確認できない。
- 設計判断が要る。
- 構成変更が要る。
- 既存の関数シグネチャ、戻り値の型、戻り値の意味、公開 API の挙動を変える破壊的変更が要る。引数のデフォルト値追加で呼び出し側が無修正で動く場合は破壊的変更ではない。
- 対象ファイル以外を書き換える必要がある。
- 共通化の観点で、対象ヘルパーまたは共通処理を実コードベース内で確認できない。
- 修正が既存仕様を変える。

上記に当たらない指摘は自動修正可能とする。修正案が明確でも、自動修正不能条件に当たる場合は修正案だけを記録する。

### 例外

観点ごとの重要度を上げる規則、判定項目、例外条件は評価観点ごとの参照資料に従う。

## 修正境界

### 変更可能範囲

変更できるのは対象にしたファイルに限る。

### 読み取り専用範囲

差分外のファイルは読み取りのみとする。コメント自体の追加、削除、書き換えは行わない。

### 直接修正できない場合

確認対象が依頼文に貼られた差分だけで実ファイルを読めない場合、または依頼や実行環境の制約でファイル編集が許可されていない場合は、直接修正せず、修正可能だが未適用としてパッチ形式または具体的な修正案を出力する。
