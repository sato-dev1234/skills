注文のキャンセル期限 — 修正箇所と関連処理

レビュー観点

注文のキャンセル期限を追加した処理と、関連する既存の実装を確認する。共通化、保守性、効率、不具合の観点から、判定と保存の役割分担、画面の表示や保存結果への影響を評価する。

観点確認内容今回の確認対象
共通化同じ役割を担う既存処理の入力・結果・利用条件を比べ、再利用できるかを確認する。一覧の判定式と、詳細画面が使う既存の期限判定関数を同じ入力で比較する。
保守性処理がどう役割を分け、どう分岐し、状態をどう管理するかから、仕様を変えたときに影響が及ぶ範囲を確認する。期限を判定する2か所の処理と、可否の判定と保存の順序を確認する。
効率処理回数や、取得・保持するデータ量が、必要以上に増えていないかを確認する。一覧1ページの表示件数と、Repositoryから受け取る件数を比較する。
不具合境界値や拒否・例外時の処理で、応答と保存結果が仕様どおりになるかを確認する。拒否時の状態更新と、期限の直前・ちょうど・直後の判定が仕様どおりかを確かめる。

変更の目的と対象

契約先は、注文をキャンセルできる日数を設定する。サーバーには、要求時の設定で判定し、出荷済みでなくても期限に達した注文の要求を拒否することを求める。一覧画面には期限切れの表示を追加する。変更対象は OrderCancelService.ts、OrderList.tsx、OrderListService.ts である。

出荷前の注文について、仕様で求める期限の扱いは次のとおりである。

日数の設定判定時刻期限による制限
未設定問わない制限しない
設定済み注文日時に日数を足した期限より前制限しない
設定済み期限と同時刻以降キャンセルできない

サーバーに求める応答と保存結果は次のとおりである。対象差分が満たしているかは、後のコードで確認する。

判定サーバーの応答
出荷済み409 を返して拒否し、保存済みのデータを変えない
出荷済みでなく、期限切れ422 を返して拒否し、保存済みのデータを変えない
受け付けた注文、操作履歴、outboxを同じトランザクションで保存する。決済済みの場合だけ返金の記録も保存する

キャンセル要求と保存

キャンセル要求の受付から保存の確定まで、期限の判定と既存の保存処理の役割を確認する。

キャンセルできるかの判定と保存の役割分担

仕様で CancelPolicy.withinWindow に求める戻り値は次のとおりである。Policy本体は掲載されていないため、実装がこの仕様を満たすかは未確認である。

日数判定時刻仕様上の戻り値
null問わないtrue

Policyは、期間内かを返す。Serviceは、受け付けるかを判断し、各Repositoryへ保存を求める。注文は、出荷済みなら既存の判定でトランザクションに入る前に拒否される。

受け付けた注文と関連記録の保存

コールバックの終わり方トランザクションがすること
正常終了した変更をコミットする
例外が発生した変更をロールバックする

Serviceは、出荷前で期間内の注文では、注文と関連記録の保存に同じtxを渡す。トランザクションは、保存中に例外が起きれば途中の変更もロールバックする。Serviceは、期限の判定を修正する際も、同じtxを渡す構成を保つ。注文が、保存に失敗しても関連記録と食い違わないためである。

返金の依頼は、保存が途中で失敗した場合は残らない。返金の依頼が、注文の更新と同じトランザクションで保存されるためである。Serviceは、キャンセルを受け付けた場合は未決済でもoutboxを作る。返金ジョブは、返金の記録がない注文には何もしない。

確認範囲は返金の依頼の保存までであり、返金ジョブ本体が仕様を満たすかは未確認である。

期限切れの要求が保存へ進む経路

不具合・保守性 — 可否の判定と状態更新

拒否した要求でも注文の更新が確定する

トランザクションは、注文の更新をコミットする。Serviceが更新後に拒否を表す値を返し、コールバックを正常終了させるためである。決済済みの注文では、キャンセル済みに変わっても返金の記録が作られず、注文と返金記録が食い違う。

期限の判定を最初の書き込みより前へ移す。受付時の保存は、既存のトランザクションにまとめたままにする。修正後は、次の結果を確かめる。

要求の扱い注文と関連記録の状態
期限切れの要求を処理した注文は関連記録とともに変わらない
受け付けた注文は関連記録と一緒に保存される

改善案は、まだ適用されておらず、実DBでも確認されていない。

一覧と注文詳細の期限表示

一覧に期限切れを知らせる表示を加える。一覧と詳細画面は同じ設定を使うため、両方の入力と判定処理を確認する。

一覧と注文詳細で期限を判定する役割

一覧は、応答に含まれる注文日時とSessionStoreの日数を使い、画面内に追加した式で期限を判定する。詳細画面は、同じ意味の入力を既存関数へ渡している。

client/src/features/orders/OrderDetail.tsx — 既存関数を使う表示判定

const canCancel = order.status !== 'shipped' &&
  withinCancelWindow(
    order.placedAt, SessionStore.cancelWindowDays(), nowMs
  );

詳細画面は、出荷状態と期限の両方を確かめてボタンを表示する。既存関数は、注文日時・日数・判定時刻から期間内かを求める。既存関数は、一覧と詳細画面で共通に使える。一覧が既存関数と入力の意味が一致し、同じクライアント環境で使えるためである。詳細画面は、出荷状態でボタンを表示するかどうかの判断を残せる。

判定は、サーバーとクライアントで別々に行うこと自体を問題にしない。サーバーが、クライアントと実行環境が異なるためである。期限の判定は、同じクライアント内で再利用できるものどうしを比べる。

同じ入力で期限の境界を確かめる

client/src/features/orders/OrderList.tsx — 一覧に追加したコード

+ const days = SessionStore.cancelWindowDays();
+ const withinWindow = days === null ||
+   Date.parse(order.placedAt) + days * DAY_MS >= nowMs;
+ const expired = !withinWindow;

一覧は、expired がtrueなら「キャンセル期限を過ぎています」を表示する。nowMs は画面の判定時刻である。

client/src/features/orders/cancelWindow.ts — 比較する既存コード

export function withinCancelWindow(
  placedAt: string, days: number | null, nowMs: number
) {
  if (days === null) return true;
  return Date.parse(placedAt) + days * DAY_MS > nowMs;
}

共通化・保守性・不具合 — 同じ役割を担う処理の比較

期限ちょうどの表示が画面間で食い違い、仕様変更時の修正箇所も増える

同じ注文でも、期限ちょうどの案内が一覧と詳細画面で食い違う。追加した式の >= が既存関数の > と異なるためである。仕様では、サーバーも期限ちょうどの要求を拒否する必要があるが、Policy本体での確認は残っている。

一覧は、既存関数を呼べば、期限を判定する場所を1つにまとめ、仕様を変えるときの修正箇所を減らせる。

一覧の取得とページ表示

一覧は、1ページに20件を表示し、各注文の日時から期限を判定する。今回の取得方法が、表示に必要な注文と値を過不足なく取得するかを確認する。

画面が必要とする注文を取得元まで辿る

期限は、表示する各注文のplacedAtから判定する。表示する行を選んだ後で期限を判定する順序は、現在の仕様に合っている。期限切れは、表示にだけ使い、行の絞り込みや並べ替えには使わないためである。

全件取得すると表示までに何件を扱うか

Serviceは、今回の差分で、Repositoryから全注文を受け取り、表示する20件を切り出す。

注文は、画面に表示しないものもRepositoryからServiceへ渡り、メモリに残る。findAllForTenantが、全注文を配列へ読み込むためである。注文は、表示が20件でも、渡してメモリに残す数が契約先の注文数に比例して増える。

既存のページ取得で必要な値が揃うか

両方のAPIは、契約先で絞り込み、注文日時・IDの降順で返す。findPageForTenant はoffsetとlimitをDBへ渡し、表示するページの注文だけを返す。placedAt も返すため、期限判定に必要な値が揃う。並び順が同じなので、ページ内の注文の順序も保てる。

比較した件数は、取得・転送・保持する注文の件数である。DB内部の走査行数と応答時間は測定していない。

効率 — 表示に必要な件数と取得件数の比較

既存のページ取得で、期限の表示を保ったまま渡す注文の数を減らせる

取得処理を findPageForTenant に戻す。一覧表示に全件取得は必要ない。Serviceが受け取る配列を、表示する20件に減らせる。件数表示に使うCOUNT取得は引き続き利用できる。
