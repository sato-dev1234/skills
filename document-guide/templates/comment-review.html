注文のキャンセル期限 — コメントのレビュー

レビュー観点

注文のキャンセル期限を追加した差分について、コメントが必要か、実装と一致するか、説明する場所が適切かを確認する。型、名前、テスト、周辺のコードだけでは分からない仕様や理由を残し、不足していれば補う。

観点確認内容今回の確認対象
コードだけで分かるか型、名前、テスト、周辺のコードから分からない仕様、理由、境界の扱いを残し、不足していれば補う。期限の判定のJSDoc、保存処理のコメント、4日前の注文を使う理由。
実装と一致するか現在の実装と食い違っていないか。応答コードのJSDoc、実装後のTODO、全件取得の理由。
説明する場所仕様や理由を、その適用範囲が分かる場所で説明しているか。JSDocの本文とタグ、無期限の扱いを説明する2か所。

変更の目的と対象

サーバーの判定と保存、画面の表示、一覧の取得、テストの準備を対象とする。OrderCancelController.ts、OrderCancelService.ts、CancelPolicy.ts、OrderList.tsx、OrderDetail.tsx、cancelWindow.ts、OrderListService.ts、OrderCancelService.test.ts のコメントと、説明が不足する箇所を確認する。

サーバー側の全関数には @param と @returns が付いている。全テストにはArrange、Act、Assertの順でステップコメントがある。どちらも変更前からの形式なので、形式を維持して内容を確認する。

期限の判定の JSDoc

server/src/orders/CancelPolicy.ts — withinWindow の JSDoc

/**
 * 注文が期限内かを返す。
 * days が null なら無期限として true。
 * 期限ちょうどは期限切れとして扱う（期限に達した時点からキャンセル不可）。
 *
 * @param placedAt 注文日時
 * @param days キャンセル可能日数
 * @param nowMs 現在時刻（ミリ秒）
 * @returns 期限内なら true
 */
export function withinWindow(placedAt: string, days: number | null, nowMs: number) {
  if (days === null) return true;
  return Date.parse(placedAt) + days * DAY_MS > nowMs;
}

null を無期限とする説明と、期限ちょうどを期限切れとする説明は残す。型 number | null だけでは、null の意味は分からない。比較演算子から境界の動作は分かるが、それが意図した仕様かは分からない。@param と @returns の形式は維持する。

説明する場所 — CancelPolicy.withinWindow の JSDoc

引数と戻り値の仕様は、その引数と戻り値のタグへ移す

仕様の内容仕様が属する先
null を無期限と扱うdays に属する
期限ちょうどを期限切れとする戻り値に属する

仕様を本文に置くと、@param days と @returns には名前の言い換えだけが残る。読み手は、仕様を本文から探すことになる。

保存処理の各行に付いたコメント

server/src/orders/OrderCancelService.ts — cancel のトランザクション内

return db.transaction(async (tx) => {
  // 注文の状態をキャンセル済みに更新する
  await OrderRepository.markCanceled(tx, order.id);
  // 決済済みの場合のみ返金額を計算する（未決済なら null）
  const refund = order.paidAt ? RefundCalculator.forOrder(order) : null;
  // 返金がある場合は返金記録を pending で挿入する
  if (refund) await RefundRepository.insert(tx, {
    orderId: order.id, amount: refund.amount, status: 'pending'
  });
  // 監査ログにキャンセル操作を記録する
  await AuditLogRepository.insert(tx, {
    action: 'order.canceled', targetId: order.id, actorId
  });
  // outbox に返金要求イベントを追加する（ワーカーが非同期で処理する）
  await OutboxRepository.insert(tx, {
    type: 'refund.requested', payload: { orderId: order.id }
  });
  // 成功を返す
  return { ok: true };
});

コードだけで分かるか — OrderCancelService.cancel の保存処理

直後の処理を言い換えた5件を削り、outboxには非同期処理と未決済時の扱いを残す

保存処理のコメント修正案がすること
直後の処理を言い換えた5件削る
outboxの1件ワーカーが非同期で処理する説明を残し、未決済でも保存する理由を補う

6件のうち5件は、呼び出し名、引数、3項演算子、if の条件から分かる内容であり、削除できる。outboxのコメントにある「ワーカーが非同期で処理する」は、直後のinsertだけからは分からないため残す。仕様では、サービスは未決済でもoutboxを作り、ワーカーは返金記録のない注文には何もしない。この扱いを、refund が null でも保存する理由として補う。
