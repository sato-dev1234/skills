注文のキャンセルに期限を設ける

この資料は、確定した要件を、設定を取得する時点、画面がボタンを出す時点、サーバーが要求を処理する時点の変更へ分ける。

画面は、サインイン直後に契約先の設定を受け取り、クライアントのストアへ保持する。利用者は、注文詳細画面からキャンセルを要求する。サーバーは、注文の状態を確かめる。サーバーは、キャンセルを受け付けた場合、注文の更新、操作履歴、返金の依頼を1つのトランザクションで書く。決済済みの場合は、返金の記録も同じトランザクションで書く。

キャンセル可能日数は、既存の設定取得に加わる。画面は、受け取った日数を使ってボタンを表示するかを決める。サーバーは、要求ごとに最新の設定を読み、期限を過ぎた要求を拒否する。返金処理は、今回は変わらない。トランザクションは、範囲が変わらない。

設計の確認結果: 実装は、確認した設計の内容で進める。画面は、判定を表示のために使う。サーバーは、キャンセルできるかどうかを最終的に判断する。

実装を止める未決事項はない。 設定を変えた直後は、画面とサーバーの判定が一時的に異なることがある。要件資料は、判定が一時的に異なることを確認済みのものとして載せている。

要件資料: refinement.html　対象: server/src/orders, server/src/session, client/src

設定の取得と保持

クライアントは、サインイン直後にGET /sessionを呼ぶ。応答は契約先と権限を含み、クライアントは応答をSessionStoreへ保持する。cancelWindowDaysは、応答とストアへ加わる。

項目値の由来変更後の扱い
tenantId, permissionsセッションが持つ契約先と、利用者が持つ権限サーバーは変更しない
cancelWindowDaystenant_settings.cancel_window_daysサーバーは応答に含め、未設定の場合はnullを返す。クライアントは受け取った値をSessionStoreに保持する。

画面での期限の判定

現在のOrderDetail.tsxは、出荷済みの注文にはキャンセルボタンを表示しない。変更後は、注文の状態とSessionStoreのキャンセル可能日数から表示するかを決める。注文が出荷済みではなく、キャンセル期限内または期限なしの場合に、キャンセルボタンを表示する。

② 期限を過ぎた注文にはボタンを出さない

追加予定: client/src/features/orders/cancelWindow.ts

export function withinCancelWindow(placedAt: string, days: number | null, now: number) {
  if (days === null) return true;
  return new Date(placedAt).getTime() + days * DAY_MS > now;
}

画面は、ボタンと期限切れの案内を出し分けるために判定する。画面は、判定をキャンセルを拒否する根拠にはしない。

サーバーでの期限の判定

入口はPOST /orders/:id/cancelである。サーバーは、出荷済みを拒否する現在の処理の直後に期限を判定する。サーバーは、キャンセル期限を過ぎたために要求を拒否する場合、422を返す。この場合、注文、返金の記録、操作履歴、返金の依頼には何も書き込まない。

③ 期限を過ぎた要求を422で拒否する
