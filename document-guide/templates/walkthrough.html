注文のキャンセルに期限を設ける

契約先の設定にキャンセル可能日数を追加する。仕様では、注文日時に設定日数を足した期限に達した注文をキャンセルできなくする。設定の取得、画面のボタン表示、サーバーの要求処理を説明する。

対象: server/src/orders, server/src/session, client/src

受注管理が今回の対象である。利用者は、注文詳細画面からキャンセルを要求する。サーバーは、注文の状態を確かめてから状態を canceled に更新する。サーバーは、操作履歴と返金の依頼を注文の更新と同じトランザクションで書く。決済済みなら、返金の記録も同じトランザクションで作る。注文は、これまでは出荷済みでなければいつでもキャンセルできた。

契約先は、キャンセル可能日数を持つ。期限を過ぎた注文は、次のように扱う。

場所期限を過ぎた注文の扱い
注文詳細キャンセルボタンを出さない
サーバー出荷済みなら409、それ以外で期限切れと判定した場合は422で拒否する

ストアは、サインイン直後に1回だけ受け取った可能日数を保持する。サーバーは、要求ごとに設定から日数を読む。

ストアは、サインイン時の可能日数を保持し続ける。対象ファイルには、可能日数を取り直す処理がない。画面は、設定を変えた後も、サインインし直すまで古い日数でボタン表示を決める。サーバーは、要求ごとに読んだ設定で CancelPolicy.withinWindow を呼び、受付可否を判断する。Policy本体がないため、期限の境界と未設定時の判定が仕様どおりかは未確認である。

サインイン時の設定取得と保持

クライアントは、サインイン直後に GET /session を1回だけ呼ぶ。応答は契約先の設定をまとめ、cancelWindowDays が応答へ加わる。クライアントは応答をそのまま SessionStore に置き、画面は後で開くときに SessionStore を読む。

項目値の由来この変更で変わる箇所
tenantId, permissionsセッションが持つ契約先と、利用者が持つ権限サーバーは変えない
cancelWindowDays契約先の設定 tenant_settings.cancel_window_days。未設定なら null新規。サーバーが応答へ追加し、クライアントがストアへ置く

① 応答に cancelWindowDays を含める

client/src/features/orders/cancelWindow.ts（新規）

export function withinCancelWindow(placedAt: string, days: number | null, now: number) {
  if (days === null) return true;
  return new Date(placedAt).getTime() + days * DAY_MS > now;
}

画面は、利用者の端末の時計とサインイン時に受け取った日数で判定する。この判定は表示の出し分けに使う。要求を受け付けるかはサーバーが決める。サーバー側の期限判定が画面と同じ条件かは、Policy本体がないため確認できていない。

画面は、サインイン中に可能日数が変わっても、サインイン時の値で判定し続ける。この差分は、期間内と表示された注文がサーバーで 422 になるときの画面表示を含まない。

キャンセル要求の処理

入口は POST /orders/:id/cancel である。サーバーは、判定の結果ごとに次のように応じる。

判定の結果サーバーがすること
出荷済み409 を返す
出荷済みでなく、期限切れと判定した422 を返す
両方の判定を通過した注文の状態、操作履歴、返金の依頼用の outbox を1つのトランザクションで保存する。決済済みの場合は返金額を計算し、返金の記録も同じトランザクションで保存する

返金ジョブは、コミット後に outbox を読む。

③ 出荷済みでなく、期限切れと判定した要求を422で拒否する

サーバーは、既存の出荷済み判定の直後に期限を判定する。日数は、要求ごとに読む契約先の設定から CancelPolicy.withinWindow へ渡す。基準時刻は now() が返すサーバーのUTC時刻である。null の扱いはPolicy本体で確認する必要がある。

export async function cancel(orderId: string, tenant: TenantContext, actorId: string) {
  const order = await OrderRepository.findForTenant(orderId, tenant.id);
  if (order.status === 'shipped') {
    throw new OrderNotCancelable('shipped');
  }
+  if (!CancelPolicy.withinWindow(order.placedAt, tenant.settings.cancelWindowDays, now())) {
+    throw new CancelWindowExceeded(order.placedAt, tenant.settings.cancelWindowDays);
+  }
  const refund = order.paidAt ? RefundCalculator.forOrder(order) : null;
  return db.transaction(async (tx) => {
    await OrderRepository.markCanceled(tx, order.id);
    if (refund) await RefundRepository.insert(tx, { orderId: order.id, amount: refund.amount, status: 'pending' });
    await AuditLogRepository.insert(tx, { action: 'order.canceled', targetId: order.id, actorId });
    await OutboxRepository.insert(tx, { type: 'refund.requested', payload: { orderId: order.id } });
  });
}

サーバーは、トランザクションを始める前に期限を判定し、拒否した場合は何も保存しない。拒否した要求は操作履歴にも残らないため、この操作履歴から期限切れで拒否した件数を数えることはできない。

CancelPolicy.withinWindow の本体は対象の差分に含まれていない。未設定を無期限とするか、期限と同時刻を期限切れとするか、クライアント側の withinCancelWindow と同じ条件かは未確認である。

サーバーは、未決済でも outbox に行を挿入する。返金ジョブは、返金の記録がない場合は何もしない。返金ジョブ本体は今回の確認範囲に含めない。
