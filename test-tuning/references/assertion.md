# 検証充足の観点

変更したテストが、対象の振る舞いを十分に検証しているかを見る。読み手は、共通の反復改善ルールを使う実行担当者と、この観点を担当する評価者。

## チェック項目

1. 検証式がない (`assert` / `expect` / 同等が 1 度も出ない)
2. 自明な検証 (モックの返り値そのまま、計算上必ず真、`not.toThrow` だけ)
3. 検証の粗さ (厳密な値比較ができるのに `toBeTruthy` / `toBeDefined`)
4. 重要な振る舞いの未検証 (対象機能の主目的が検証されていない)

## この観点だけの判定規則

次は critical に格上げする:

- テスト名と検証式の意図不一致 (例: `test("returns null")` の本文が `expect(x).toBeTruthy()`)
- 検証式そのものが存在しない

検証の粗さ (`toBeTruthy` / `toBeDefined` / `toBeNull` 単独などで済ませている)、自明な検証は high。重要な振る舞いの未検証 (具体的に何の検証が欠けているか言える) は medium。

## この観点だけの自動修正可能性

「テスト名と検証式の意図不一致」(例: `test("returns null")` の本文が `expect(x).toBeTruthy()`) は**意図変更ではない**。テスト名を意図の真として、検証式を意図に揃える修正は自動修正可能とする。

## 評価者へ渡す依頼

```
あなたはテストコード差分を検証充足の観点で評価する読み取り専用の評価者です。修正はしません。

## 対象の差分
採用した差分全体を含める。

## この観点で見ること
1. 検証式がない (assert / expect / 同等が 1 度も出ない)
2. 自明な検証 (モックの返り値そのまま、計算上必ず真、not.toThrow だけ)
3. 検証の粗さ (厳密な値比較ができるのに toBeTruthy / toBeDefined)
4. 重要な振る舞いの未検証 (対象機能の主目的が検証されていない)

## 制約
- テスト名と検証式の意図不一致、検証式の不在は critical で返す
- 読み取り専用。テストコードは修正しない

## 指摘の返し方
各指摘について次を添える:
- 対象ファイルと行
- 指摘の要約と内容
- 重要度 (critical / high / medium のいずれか。判断に迷えば書かなくてよい。最終判定は呼び出し側が決める)
- 修正可能性候補 (自動修正可能 / 自動修正不能。判断に迷えば書かなくてよい)
- 根拠 (行番号と該当コード片 1-3 行。行番号だけは不可)
- 修正案
```
