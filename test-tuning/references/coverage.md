# 網羅性の観点

変更したテストが、境界条件・異常経路・重要な分岐を取りこぼしていないかを見る。読み手は、共通の反復改善ルールを使う実行担当者と、この観点を担当する評価者。

## チェック項目

1. 境界条件の欠落 (空配列、空文字、上限、下限、0、null、undefined)
2. 異常経路の欠落 (エラー時、例外時、認可拒否時、入力不正時)
3. 重複したテスト (同じ振る舞いを繰り返し確認)
4. 対象機能の重要な分岐の未確認

## この観点だけの判定規則

この観点だけで重要度を上げる規則は無い。重要度はテストチューニングの分類規則に従う (重要な振る舞いの未検証・重複したテストは medium)。

## この観点だけの自動修正可能性

網羅性の観点で具体的に欠落が指摘された場合に限り、新規テストケースを既存テストファイルへ最小範囲で追加してよい。新規テストファイルの作成は、対象パスと公開点が明示できる場合だけ行う。対象機能の意図(期待値、検証対象)を変える必要がある追加は自動修正不能とする。

## 評価者へ渡す依頼

```
あなたはテストコード差分を網羅性の観点で評価する読み取り専用の評価者です。修正はしません。

## 対象の差分
採用した差分全体を含める。

## この観点で見ること
1. 境界条件の欠落 (空配列、空文字、上限、下限、0、null、undefined)
2. 異常経路の欠落 (エラー時、例外時、認可拒否時、入力不正時)
3. 重複したテスト (同じ振る舞いを繰り返し確認)
4. 対象機能の重要な分岐の未確認

## 制約
- 欠落を指摘するときは、具体的に何の検証が欠けているかを示す (抽象的な「網羅不足」では指摘にしない)
- 読み取り専用。テストコードは修正しない

## 指摘の返し方
各指摘について次を添える:
- 対象ファイルと行
- 指摘の要約と内容
- 重要度 (critical / high / medium のいずれか。判断に迷えば書かなくてよい。最終判定は呼び出し側が決める)
- 修正可能性候補 (自動修正可能 / 自動修正不能。判断に迷えば書かなくてよい)
- 根拠 (行番号と該当コード片 1-3 行。行番号だけは不可)
- 修正案
```
