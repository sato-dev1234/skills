# テストチューニングの対象と修正範囲

このファイルは、テストチューニングで扱う対象、評価、指摘の扱い、修正範囲を定める。評価者の起動、評価結果の整理、重複指摘の統合、修正、再評価、起動できない場合の扱いは共通の反復改善ルールに従う。判定項目の詳細は観点別の参照資料、停止判断と出力規則は完了判定の参照資料を正本にする。

## 対象

### 入力

確認対象の差分は次で決める。

| 条件 | 扱い |
|---|---|
| 依頼で差分取得コマンドが指定されている | 指定されたコマンドを採用する |
| 差分取得コマンドの指定がない | `git diff HEAD` を見る |
| 未追跡ファイルがある | `git status --short` と `git ls-files --others --exclude-standard` で確認し、新規追加ファイルとして内容を読む |
| 差分取得コマンドが使えない、または確認対象が空である | 依頼で明示された差分ファイルまたは対象ファイルだけを読む。明示された対象がなければ「確認対象が特定できない」と明示して対象外停止にする |

### 対象判定

| 入力 | 対象判定 | 扱い |
|---|---|---|
| テストファイルの変更 | 対象 | 対象テストファイルだけを評価対象にする |
| 本体コードの変更のみ | 対象外 | 本体コード品質の確認が必要な対象として示す |
| 設定、文書、画像、ロックファイル | 対象外 | 評価せず対象外として報告する |

テストファイルは、テスト専用ディレクトリ、標準的なテストファイル名、言語固有のテストサフィックスで判定する。

### 対象範囲

対象テストファイルと対象外ファイルが混在する場合は、対象テストファイルだけを評価対象にする。対象外ファイルは評価対象に含めず、別責務の確認が必要な場合は対象と責務境界を出力で示す。

対象外ファイルの内容は、テスト意図や期待値を推定する補助情報として使ってよい。ただし、対象外ファイルだけを根拠に期待値を確定しない。

### 根拠の示し方

指摘の根拠となる行番号は変更後ファイルの行番号で記す。実ファイルを読めるなら実ファイルの行番号、読めない場合は変更後側の開始行を差分ヘッダから算出する。

### 対象外時の扱い

対象外として停止する場合は、停止理由、確認した入力、評価を実施していない事実を出力する。指摘、修正案、検証結果を混ぜない。

## 評価

### 評価観点

各観点のチェック項目、観点ごとの判定規則、評価者へ渡す依頼は参照資料に従う。

| 評価観点 | 参照資料の責務 | 読む資料 |
|---|---|---|
| 検証充足 | 対象の振る舞いを十分に検証しているかの評価 | 検証充足の参照資料 |
| 独立性 | 共有状態や実行順への依存の評価 | 独立性の参照資料 |
| 安定性 | 時間、順序、非決定的データ、環境差で壊れる可能性の評価 | 安定性の参照資料 |
| 網羅性 | 境界条件、異常経路、重要な分岐の取りこぼしの評価 | 網羅性の参照資料 |

この表にある各評価観点は、共通の反復改善ルールでいう評価の区切りとして扱う。観点ごとの評価者は対象を変更せず、修正、評価結果の統合、再評価、完了判定は共通の反復改善ルールと完了判定の参照資料に従う。

### 評価者へ渡す情報

各評価観点の依頼には、採用した差分全体、対象テストファイル、対象外ファイルの一覧、読み取り専用制約を含める。評価者はテストコードを修正しない。

### 責務外

本体コードの品質、コメント・テスト命名の整備、受入条件との整合は本スキルの責務外である。必要な場合は、対象と確認したい責務を分けて示す。

## 指摘の扱い

### 評価結果の必須情報

評価者の返却は、共通の反復改善ルールの `指摘あり`、`指摘なし`、`評価不能` に整理する。テストチューニングでは次の情報を必須にする。

| 状態 | 必須情報 |
|---|---|
| 指摘あり | 評価観点、対象ファイルと行、指摘の要約と内容、重要度候補、修正可能性候補、根拠コード、修正案、評価者が迷った点 |
| 指摘なし | 評価観点、確認範囲、該当指摘なしの理由、評価者が迷った点 |
| 評価不能 | 評価観点、理由、不足入力、確認できた範囲、評価者が迷った点 |

指摘の根拠は、行番号と該当コード片 1-3 行を最小要件とする。行番号のみは不可。

### 重複指摘のまとめ方

評価観点、対象テストファイル、問題箇所、落ちた判定項目、修正意図で同じ問題かを判定する。同じ箇所への重複指摘は統合する。観点が違っても、同じテストの同じ問題を同じ修正意図で解消する場合は 1 件にする。

### 分類

各指摘の重要度は、テストの信頼性にどれだけ深く関わる問題かで決める。当てはまる最も重い段階を採る。観点ごとの重要度を上げる規則は参照資料に従う。

| 重要度 | 当てはまる状態 |
|---|---|
| critical | テストが意味を成さない、または確実に壊れる。テスト名と検証式の意図不一致、検証式の不在、モジュールレベルの可変共有状態による実行順依存、テスト同士の順序依存、時間待ち、非決定的データ、環境差で壊れる固定値依存がある |
| high | テストは動くが検証として弱い。検証が粗い、自明な検証、テストごとの事前処理または後始末の不足がある |
| medium | 重要な振る舞いが未検証で、何の検証が欠けているか具体的に言える。重複したテストがある |

これらより軽い問題は出力しない。本当に害があるなら medium 以上に格上げするか、判定を取り下げる。

### 自動修正可能性

次のいずれかに当たる指摘は自動修正不能とする。

- テストの意図、期待値、対象機能、検証対象を変える必要がある。
- 対象機能と無関係なテストの作り替えが要る。
- 本体コードの API 変更が必要で、テスト側だけでは閉じない。
- 対象ヘルパー、公開点、キャッシュ消去などのクリーンアップ関数を実コードベースで確認できない。
- 対象テストファイル以外を書き換える必要がある。ただし、網羅性の観点で具体的に欠落が指摘され、対象パスと公開点を明示できる新規テストファイルの作成は対象外にしない。

上記に当たらない指摘は自動修正可能とする。観点ごとの規則は、自動修正不能条件に当たらない場合だけ適用する。

### 例外

観点ごとの重要度を上げる規則、判定項目、例外条件は評価観点ごとの参照資料に従う。

## 修正境界

### 変更可能範囲

変更できるのは対象にしたテストファイルに限る。網羅性の観点で具体的な欠落があり、対象パスと公開点を明示できる場合だけ、新規テストファイルを最小範囲で作成してよい。

### 読み取り専用範囲

本体コード、対象外ファイル、差分外の既存テストファイルは読み取りのみとする。

### 直接修正できない場合

確認対象が依頼文に貼られた差分だけで実ファイルを読めない場合、または依頼や実行環境の制約でファイル編集が許可されていない場合は、直接修正せず、修正可能だが未適用としてパッチ形式または具体的な修正案を出力する。
