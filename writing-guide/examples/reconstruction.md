# 原文からツリーを作る例

## 依頼と原文

依頼は、次の注文キャンセルの要件メモを、仕様を確認する読み手へ渡す文章に整えることである。[文章の規則](../references/writing.md)に従って原文全体をツリーにし、[ツリーから文章を書く例](composition.md)で、未解決箇所を除く書き直しを示す。

### 原文

今回の変更では、注文のキャンセル可能期間の設定機能を導入します。これまでは出荷前であればいつでもキャンセルが可能でしたが、注文から長く経過した後のキャンセルが出荷準備や在庫計画とぶつかるという問い合わせが契約先から続いていました。そのため、契約先ごとに、注文から何日以内であればキャンセルを可能とするかを設定できるようにします。注文詳細画面では、期間を過ぎた注文に対するキャンセルボタンの非表示化と、「キャンセル期限を過ぎています」という案内の表示を行います。期間を設定するときは、対象になる注文がどれだけあるかを設定の前に確かめます。

期間の設定値はサインイン直後に1度だけ取得され、画面側での保持が行われます。キャンセルが受け付けられた場合は注文がキャンセル済みとなり、決済済みであれば返金手続きが進みます。この返金処理については今回変更しません。期間が未設定の契約先については、従来どおり出荷前であればいつでもキャンセルできます。既存の契約先の操作に対して、予告のない制限を加えないためです。なお、出荷済みの注文には、従来と同じくキャンセルボタンを表示しません。

キャンセル要求の受付時には、サーバー側で最新の設定を用いた最終的な可否判定を実施します。出荷済みの注文や、期間を過ぎた注文は受け付けません。画面の表示状態や利用者の端末時刻にかかわらず、誤ったキャンセルを防ぐ必要があるためです。受け付けなかった場合は、注文の変更や操作履歴への記録は行いません。期間の導入に伴う返金処理の変更はありません。

管理者による期間の変更があっても、サインイン中の画面には変更前の値が保持されます。サーバーの判定には変更後の値がすぐ反映されるため、画面とサーバーの即時的な整合性は保証されません。この差異は、期間の短縮の直後においては、ボタンが表示されているにもかかわらず要求が拒否される事象として、期間の延長の直後においては、キャンセル可能な注文にボタンが表示されない事象として現れます。サインインし直すと画面にも変更後の期間が反映されます。このように設定の反映時点が異なる点には注意が必要です。

## 文章が前提とする知識

原文は、契約先が設定できる内容と、設定によって注文の扱いや画面の表示がどう変わるかを説明している。読み手には、注文、出荷、決済、設定変更と画面操作の知識を前提とする。

画面とサーバーの違いは、表示と受付判定をそれぞれ担う役割として説明できる。設定値が一致するかを理解するために、情報科学の専門概念を知っている必要はない。この前提をツリーに記録し、各項目の呼び方を決めるときに使う。

## 主張と関係の整理

構成は操作場面ごとに分ける。話題は、原文に最初に現れる順に「契約先ごとに期間を決める」「注文詳細画面」「期間の設定値を反映するとき」「キャンセル要求を受け付けるとき」とする。以下の `@1-2` は第1段落第2文を表す。

| 原文の内容 | ツリーへの整理と理由 |
|---|---|
| 期間を過ぎた注文のボタンを隠し、案内を表示する（1-4） | 主体、条件、表示対象、動作、案内の内容を分ける。出荷済みの場合と合わせ、条件別の表示として対応にする |
| 設定値を取得して画面で保持する（2-1） | 主体を画面として共有し、取得の時点・回数、取得後に保持する対象を分ける。取得して保持する経過を説明するため、並列した結果の列挙にはしない |
| 過去の受付条件と、現在の未設定時の受付条件（1-2、2-4） | 時点と条件が異なるため、別の項目として残す |
| 未設定時の扱いと、その理由（2-4、2-5） | 既存の操作を予告なく制限しないことを、未設定時の項目の理由にする |
| 返金処理を変更しないという説明（2-3、3-5） | 同じ主張なので1項目にまとめ、両方の原文位置を付ける |
| 出荷済みや期限切れの要求を拒否する理由（3-2、3-3） | 画面や端末時刻にかかわらず誤ったキャンセルを防ぐ必要性を、拒否の項目に付ける |
| 画面とサーバーの設定値がすぐ一致する保証がないことと、その理由（4-1、4-2） | 画面が以前の値を保持する項目を残し、サーバーが変更後の値をすぐ使うことを、すぐ一致する保証がない理由として記録する |
| 期間の短縮・延長による表示と受付結果（4-3） | 原文が述べる事象を変更の種類ごとに対応させる。サインインし直すまでの共通場面は4-1と4-4から取る。適用する注文条件は未解決とし、完成文への反映を保留する |
| 拒否後に注文を変更せず操作履歴にも記録しない（3-4） | サーバーと拒否の条件を共有し、対象と動作の異なる2項目を列挙にする |
| 設定が反映される時点への注意（4-5） | 読み手への指示として残す |

注文詳細画面では、各条件についてボタンと案内をどう表示するかが対応する。期限切れと出荷済みは同時に成立し得るため、各条件を独立して適用する。出荷済みの場合の案内は原文に記載がなく、表示しないとは判断しない。

受付後に起こることと、拒否後に行わないことは、それぞれ共通条件の下に並ぶ結果なので列挙にする。返金だけに掛かる決済済みの条件は、返金の項目に残す。

## 言葉の選択

各項目が指す内容を、文章が前提とする知識に照らして確認する。設定や操作の結果を具体的に説明し、要件を理解するために必要な区別と画面上の案内は残す。

| 原文の表現 | この項目での意味 | 採用する表現と理由 |
|---|---|---|
| 即時的な整合性は保証されない | 画面とサーバーの設定値がすぐ一致する保証がない | 「期間の設定値がすぐに一致することは保証されない」。読み手は設定値の違いとして理解できる |
| 最新の設定を用いた最終的な可否判定を実施する | サーバーが受付時の設定でキャンセルできるかを判断する | 「キャンセル要求の受付時に、最新の設定でキャンセルできるかを判断する」。判断する側、時点、設定を具体的に残す |
| キャンセルボタン、ボタン | キャンセルを要求する画面の操作部品 | 「キャンセルボタン」。画面での役割が分かり、同じ部品を指すことも明確になる |
| 返金手続き、返金処理 | 決済済みの注文をキャンセルした後に進む行為 | 「返金手続き」。同じ行為の呼び方を揃え、決済済みという条件は項目に残す |
| 期間、期限 | キャンセルできる日数と、キャンセルできなくなる時点 | それぞれ残す。日数と時点を区別する必要がある |
| 画面、サーバー | 表示と受付判定を担い、設定を使う時点が異なるもの | それぞれ残す。項目の動作が役割を説明しており、違いを理解するために必要である |
| 「キャンセル期限を過ぎています」 | 画面に出す案内文 | そのまま残す。実際の表示内容を指定しているためである |
| 反映時点が異なる | 設定が反映される時が違う | 「設定が反映される時の違い」。読み手に注意を求める内容を具体的にする |

## 原文との対応

| 原文位置 | 行き先 |
|---|---|
| 1-1 | 文書の表題 |
| 1-2 | 過去の挙動と、期間を設定できる理由 |
| 1-3、1-5、2-4、2-5 | 契約先ごとの設定、設定前の確認、未設定の挙動と理由 |
| 1-4、2-6 | 条件別の表示にある3項目と共通情報 |
| 2-1、4-1、4-2 | 設定値の取得・保持と、変更後の挙動・理由 |
| 4-3 | 原文が述べる2つの表示差と、適用する注文条件の不足 |
| 4-4、4-5 | サインインし直した後の反映と、読み手への注意 |
| 2-2、2-3 | 受付後の注文と返金、返金手続きの不変更 |
| 3-1、3-2、3-3、3-4 | 受付時の判定、拒否と理由、拒否後の不変更 |
